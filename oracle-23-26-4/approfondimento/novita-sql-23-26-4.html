FETCH FIRST … FOR UPDATE [SKIP LOCKED]

Top-N con FOR UPDATE e SKIP LOCKED

Una query top-N ora può bloccare le righe che restituisce. Con SKIP LOCKED le righe già bloccate da altre transazioni vengono saltate e non contano nel limite: la query continua finché trova N righe libere.

La sessione 1 tiene bloccato il dipendente 100. La sessione 2 chiede tre righe: con ROWNUM la riga bloccata occupa uno dei tre posti e ne arrivano due; con FETCH FIRST non conta e ne arrivano tre.

L'esempio della slide

where  employee_id = 100;

from   hr.employees

    select employee_id from hr.employees
    order  by employee_id
    for    update skip locked;
  type t_ids is table of hr.employees.employee_id%type;
  l_ids t_ids;
begin
  open c;
  fetch c bulk collect into l_ids limit 3;
  -- elaborazione di l_ids ...
  close c;
  commit;
end;

Esempio completo: una coda di lavori

Il caso d'uso tipico: più processi prelevano lavori dalla stessa tabella senza aspettarsi a vicenda e senza prendere due volte lo stesso lavoro.

Tabella
create table jobs (
  job_id     number generated always as identity primary key,
  payload    varchar2(100) not null,
  stato      varchar2(10) default 'NUOVO' not null,
  creato_il  timestamp default systimestamp not null,
  preso_da   varchar2(30),
  finito_il  timestamp
);
create index jobs_coda_ix on jobs (stato, creato_il);

insert into jobs (payload)
select 'job ' || level connect by level <= 20;
commit;
Worker23.26.4
declare
  cursor c_lotto is
    select job_id, payload
    from   jobs
    where  stato = 'NUOVO'
    order  by creato_il, job_id
    fetch  first 5 rows only
    for    update skip locked;
begin
  for j in c_lotto loop
    -- elaborazione di j.payload ...
    update jobs
    set    stato     = 'FATTO',
           preso_da  = sys_context('userenv', 'sid'),
           finito_il = systimestamp
    where  job_id = j.job_id;
  end loop;
  -- il COMMIT chiude il lotto e rilascia i lock
  commit;
end;
/

Due worker avviati insieme dovrebbero ricevere lotti diversi (1–5 e 6–10): è il comportamento descritto dalla documentazione, non l'ho potuto eseguire senza la 23.26.4.

Le quattro varianti di FOR UPDATE

ClausolaSe una riga è bloccata da un altro
for updateAspetta che si liberi. Ordine rispettato, nessun salto.
for update nowaitErrore immediato ORA-00054.
for update wait 5Aspetta fino a 5 secondi, poi errore.
for update skip lockedSalta la riga. Con FETCH FIRST la riga saltata non conta nel limite.

Attenzione

  • Senza ORDER BY le prime N righe sono righe qualsiasi.
  • SKIP LOCKED rinuncia all'ordine rigoroso: un worker può finire il job 6 prima che un altro finisca il 5. Per una coda va bene, per elaborazioni strettamente sequenziali no.
  • Indice. Serve un indice che porti subito alle righe da prelevare (qui stato, creato_il); senza, ogni worker legge tutta la tabella.
  • Transazioni brevi. I lock restano fino a COMMIT o ROLLBACK.
  • Row limiting partizionato. La documentazione garantisce che le righe bloccate non contano nel limite per il row limiting non partizionato, cioè FETCH FIRST senza PARTITION BY.

UUID ( 7 ) · UUID ( 5, namespace, nome )

UUID versione 7 e versione 5

UUID() esiste dalla 23.9 e genera UUID casuali, versione 4, come RAW(16). Ora genera anche la versione 7, che comincia con un timestamp ed è quindi ordinata nel tempo, e la versione 5, ricavata in modo deterministico da un namespace e da un nome.

Come funziona la v5, in SQL

La v5 è l'hash SHA-1 del namespace seguito dal nome, troncato a 128 bit, con versione e variante sovrascritte. Questa query ricostruisce i valori della slide senza UUID(5, …): utile per capire il meccanismo e per generare le stesse chiavi su release precedenti.

SQLfino a 23.26.3
select level n,
       utl_raw.bit_or(
         utl_raw.bit_and(
           utl_raw.substr(
             standard_hash(utl_raw.concat(hextoraw('6BA7B8119DAD11D180B400C04FD430C8'),  -- namespace URL
                                          utl_raw.cast_to_raw('test.com/' || level)), 'SHA1'), 1, 16),
           hextoraw('FFFFFFFFFFFF0FFF3FFFFFFFFFFFFFFF')),      -- azzera versione e variante
         hextoraw('00000000000050008000000000000000')) uuid_v5  -- versione 5, variante RFC
connect by level <= 5;

Chiave stabile per caricamenti ripetibili

La v5 dà sempre lo stesso UUID per lo stesso nome. Ricaricando lo stesso file la chiave non cambia: niente duplicati e niente tabella di corrispondenza. Un'applicazione che usa uuid5(NAMESPACE_URL, …) ottiene lo stesso valore.

              codice, nome
       from   stg_clienti) s
on (d.id = s.id)
when matched then
  update set d.nome = s.nome
when not matched then
  insert (id, codice, nome) values (s.id, s.codice, s.nome);

Misura: cosa succede all'indice di chiave primaria

200.000 inserimenti riga per riga in tabelle con chiave primaria RAW(16), su 23.26.3. La v7 è emulata con lo stesso layout di bit e con bit casuali dentro il millisecondo, come nella slide. Il ritmo è in righe per millisecondo sullo stesso indice: 5 righe/ms sono 5.000 righe al secondo. Fonti: statistiche leaf node splits e INDEX_STATS.

Foglie dell'indice e riempimento medio dei blocchieseguito 23.26.3
CHIAVE                FOGLIE PCT RIEMPIMENTO
--------------------- ------ --- -----------
IDENTITY (sequenza)      374 100 ██████████
UUID v7, 1 riga/ms       676 100 ██████████
UUID v4 (casuale)        985  69 ██████▉
UUID v7, 5 righe/ms     1154  59 █████▉
UUID v7, 100 righe/ms   1328  51 █████▏
UUID v7, 25 righe/ms    1333  51 █████▏
  • Sequenza: chiavi crescenti e corte, split 90-10, blocchi pieni al 100%. Resta la chiave più compatta.
  • v4: chiavi sparse, split 50-50, blocchi pieni al 69% circa, il valore tipico degli inserimenti casuali. Ogni insert può toccare qualsiasi blocco dell'indice: quando l'indice non sta in memoria diventano letture da disco.
  • v7 fino a 2 righe/ms: le chiavi arrivano in ordine e l'indice si comporta come con una sequenza: 100% e insert concentrati sul bordo destro.
  • v7 da 5 righe/ms in su: nello stesso millisecondo l'ordine è casuale, il blocco di destra si divide 50-50 e la metà sinistra non riceve più chiavi. Risultato: blocchi pieni al 51%, peggio di v4.
  • Caricamenti massivi: lo stesso carico a 100 righe/ms con INSERT /*+ APPEND */ (direct-path) produce un indice pieno al 100% (676 foglie contro 1.329), perché l'indice viene aggiornato in blocco a fine istruzione.

Attenzione

  • Un v7 rivela quando è stato creato. Chi vede l'ID vede la data e l'ora.
  • La v5 è deterministica. Chiunque conosca namespace e nome la ricalcola: non usarla come token segreto. Normalizza il nome prima di calcolarla: 'Test.com/1' e 'test.com/1' danno UUID diversi, e con caratteri non ASCII conta la codifica dei byte.
  • Conserva gli UUID come RAW(16): 16 byte contro i 36 di VARCHAR2(36), confronti più veloci e indici più piccoli. Il formato con i trattini serve solo in visualizzazione.
  • PL/SQL. Su 23.26.3 UUID e RAW_TO_UUID non si possono chiamare come funzioni PL/SQL (PLS-00201): si usano dentro un'istruzione SQL, per esempio select raw_to_uuid(uuid()) into l_id;.

BAR_CHART ( valore, massimo, minimo, larghezza, simbolo )

BAR_CHART

Una funzione che restituisce una barra di testo proporzionale a un valore. Serve a vedere una distribuzione direttamente nel risultato di una query, in SQL*Plus, SQLcl o qualsiasi altro client.

Sintassi23.26.4
BAR_CHART ( valore [, massimo [, minimo [, larghezza [, simbolo ] ] ] ] )
ParametroPredefinitoSignificato
massimo100Valore che riempie tutta la barra. Viene prima del minimo.
minimo0Valore che corrisponde alla barra vuota.
larghezza10Caratteri della barra piena.
simboloblocchi UnicodeSe omesso, la parte frazionaria è disegnata con i blocchi parziali ▏▎▍▌▋▊▉; con un simbolo scelto, per esempio '#', la lunghezza viene arrotondata all'intero.

La lunghezza vale (valore − minimo) ÷ (massimo − minimo) × larghezza. Oltre il massimo la barra resta piena.

Le stesse barre si ottengono con RPAD per un simbolo ASCII e con UNISTR per i blocchi Unicode. È anche il modo più chiaro di spiegare cosa calcola la funzione.

SQLfino a 23.26.3
-- come bar_chart(salary, 24000, 0, 20, '#')

       rpad('#', round((salary - 0) / (24000 - 0) * 20), '#') barra
from   hr.employees;

-- come bar_chart(salary, 24000): blocchi pieni + un blocco parziale in ottavi

  select salary, least(greatest((salary - 0) / (24000 - 0), 0), 1) * 10 x
  from   hr.employees
)
select salary,
       replace(rpad(' ', trunc(x)), ' ', unistr('\2588'))
       || substr(unistr(' \258F\258E\258D\258C\258B\258A\2589'), round(mod(x, 1) * 8) + 1, 1) barra
from   d;

  • Caratteri. I blocchi Unicode richiedono un client e un font che li mostrino; se vedi simboli strani usa un simbolo ASCII come '#'.

CREATE MACRO

CREATE MACRO

Le SQL macro esistono dalla 19c (di tabella) e dalla 21c (scalari), ma si scrivevano come funzioni PL/SQL che restituiscono il testo SQL dentro una stringa. CREATE MACRO permette di scrivere direttamente il SQL: una macro scalare è un'espressione riutilizzabile, una macro di tabella è una vista con parametri.

Macro di tabella: prima e ora

Fino a 23.26.3

SQLfino a 23.26.3
create or replace function dept_totals ( hired_after date )
  return varchar2 sql_macro(table) is
begin
  return q'[select department_id, count(*) emp#
            from   hr.employees
            where  hire_date > hired_after
            group  by all]';
end;
/

create or replace function get_3_rows ( table_name dbms_tf.table_t )
  return varchar2 sql_macro(table) is
begin
  return 'select * from table_name fetch first 3 rows only';
end;
/

Con 23.26.4

SQL23.26.4
/* Parameterized view */
create or replace macro dept_totals ( hired_after date ) is
  select department_id, count(*) emp# from hr.employees
  where  hire_date > hired_after group by all;

/* Polymorphic view - pass table name as parameter */
create or replace macro get_3_rows ( table_name table ) is
  select * from table_name fetch first 3 rows only;
Uso (identico nelle due forme)

left join dept_totals ( date '2015-01-01' ) using ( department_id );

Cosa cambia rispetto alla funzione SQL_MACRO

  • Niente PL/SQL e niente stringhe. Spariscono return varchar2, begin … end, gli apici raddoppiati e q'[…]'; l'editor evidenzia e completa il SQL.
  • Gli errori di sintassi emergono subito. Il corpo fa parte dell'istruzione, quindi un errore fa fallire il CREATE. Con la funzione classica il testo è una stringa: la funzione viene creata senza errori e il problema emerge solo quando qualcuno la usa.
  • Macro nella clausola WITH. Dalla 23.26.4 si possono usare dentro la WITH; prima l'errore era ORA-64630 (fonte: blog Oracle sulle viste con parametri).

Finestre temporali nella FROM

Quattro funzioni da usare nella FROM: assegnano ogni riga a una o più finestre di tempo e aggiungono le colonne WINDOW_START e WINDOW_END, su cui poi si aggrega. Il modello è quello delle window table function di Apache Flink, applicato ai dati delle tabelle.

FunzioneArgomenti dopo tabella e COLUMNS(colonna)FinestreUna riga finisce in
TUMBLEdurataConsecutive, stessa durata, senza sovrapposizioni.1 finestra
HOPpasso, durataStessa durata, una nuova ogni passo: si sovrappongono.durata ÷ passo finestre
CUMULATEpasso, durata massimaStesso inizio, si allungano di un passo fino al massimo.tutte quelle che finiscono dopo di lei
SESSIONSpausaDecise dai dati: se tra due righe consecutive passa più della pausa, ne inizia una nuova.1 finestra

Gli argomenti di tempo sono letterali INTERVAL (anni e mesi, oppure giorni, ore, minuti e secondi). In HOP il passo viene prima della durata.

-- CUMULATE ( ..., interval '2' year, interval '10' year ): 10 / 2 = 5 passi
select time_bucket(e.hire_date, interval '10' year, date '1970-01-01') window_start,
       add_months(time_bucket(e.hire_date, interval '10' year, date '1970-01-01'), 24 * n.k) window_end,
       count(*)
from   hr.employees e
cross  join (select level k connect by level <= 5) n
where  e.hire_date < add_months(time_bucket(e.hire_date, interval '10' year, date '1970-01-01'), 24 * n.k)
group  by all
order  by window_start, window_end;
SESSIONSfino a 23.26.3
-- SESSIONS ( ..., interval '2' year ): isole e buchi con LAG e somma progressiva
with segnate as (
  select hire_date,
         case when hire_date <= add_months(lag(hire_date) over (order by hire_date), 24)
              then 0 else 1 end nuova_sessione
  from   hr.employees
), numerate as (
  select hire_date, sum(nuova_sessione) over (order by hire_date) sessione
  from   segnate
)
select min(hire_date) window_start, add_months(max(hire_date), 24) window_end, count(*)
from   numerate
group  by sessione
order  by window_start;

Per CUMULATE e SESSIONS i risultati coincidono con quelli delle slide (1, 14, 53, 96, 107 e una sessione da 107 righe).

Attenzione

  • Le finestre vuote non compaiono. Nell'esempio delle vendite non c'è la riga 07:00–08:00. Se servono gli zeri, fai un outer join con un calendario.
  • HOP e CUMULATE moltiplicano le righe. La somma dei conteggi delle finestre non è il totale: nella slide di HOP fa 428, cioè 4 × 107.
  • Inizio incluso, fine esclusa. Una vendita delle 09:00:00 cade nella finestra 09:00–10:00.
  • Allineamento fisso. Le finestre partono da istanti fissi (anni pari, ore piene), non dalla prima riga. Per un'origine diversa, come un anno fiscale che inizia ad aprile o turni che partono alle 6:00, TIME_BUCKET accetta un'origine esplicita.
  • Batch, non streaming. I nomi vengono dallo streaming SQL, ma qui le funzioni lavorano sui dati presenti nella tabella al momento della query.
